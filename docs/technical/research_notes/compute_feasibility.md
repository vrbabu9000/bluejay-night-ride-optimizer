Evidence labels: **VERIFIED** (read in a primary source or measured locally in this session), **SECONDARY** (secondhand or recalled, not re-read), **INFERENCE** (reasoned from verified facts), **HYPOTHESIS** (plausible, untested), **ESTIMATE** (my number, assumptions stated).

## 0. Summary

1. The simulation does not need OSRM at run time. All 188 x 188 times are already in `data/processed/tt_locations_v2.csv` (35,344 rows). OSRM is a one-off data tool; only the person who builds new matrices needs it. (INFERENCE from the files; confirm the simulator only looks up the matrix.)
2. The pinned image **is** published for linux/amd64 (VERIFIED, section 5). Cross-machine bit-identity of travel times is not guaranteed and is untested. Make the **matrix CSV plus sha256 the canonical artifact**, not the 1.1 GB routing folder.
3. Exact methods (MILP) are viable only at the 2-van/16-request levels (and probably up to roughly 5 vans with about 10-15 open requests per epoch). At 25 vans and 300 requests/hour a per-epoch MILP is out of reach in a 2-minute cadence; a heuristic is the only option (ESTIMATE, section 2).
4. Recommended stack: pure Python/numpy simulation and insertion + local search heuristic; HiGHS (MIT) via `highspy` for exact benchmarks; OR-Tools/PyVRP only as optional cross-checks. No GPU role.
5. Time-limited solves are not reproducible across machines. Use node/iteration limits as the primary budget and report status and gap with every solve.

**Determinism controls (general principles; solver-specific claims above are labeled).**
- A wall-clock `time_limit` makes results depend on CPU speed, load and thread scheduling. Two machines will stop at different incumbents. Use a deterministic budget as the primary stop: node limit (`mip_max_nodes`), iteration/solution limits for heuristics, or your own iteration counter for local search. Keep a wall-clock cap only as a safety net, and log whenever it fires.
- Threads: use 1 thread per solve for reported results; parallelize across runs. Multi-thread MIP is a common source of run-to-run variation (INFERENCE, general MIP behavior; verify for HiGHS with the repeat test).
- Seeds: pass an explicit seed to every stochastic component (heuristic, solver), derived from the experiment seed (section 6).
- Always record per solve: status (optimal / limit reached), objective, best bound, gap, nodes, seconds, solver and version.

## 4. GPU

Honest answer: **no useful role.** (a) The Mac has no CUDA; cuOpt needs an NVIDIA GPU on Linux (VERIFIED). (b) Our per-epoch problems are tens to a couple of hundred stops with strong sequential structure; the heuristic is branchy local search, which does not map well to GPUs at this size (INFERENCE). cuOpt targets large routing problems; its MIP is beta with weak optimality proofs (VERIFIED), so it cannot replace the exact benchmark. (c) Adding a GPU path would hurt reproducibility (driver/CUDA/hardware dependence) and reviewers could not rerun it. If experiments are too slow, the fixes are algorithmic (incremental insertion cost evaluation, numpy-vectorized neighbor evaluation, fewer re-plans), more CPU workers, or a compiled inner loop (e.g., numba/C++) after profiling.

## 5. OSRM portability

**5.1 Is the pinned image published for amd64? YES (VERIFIED).** `docker buildx imagetools inspect ghcr.io/project-osrm/osrm-backend:v6.0.0` (read-only, run in this session) returned an OCI index with digest `sha256:729461bc...eb564`, listing:
- linux/amd64 manifest `sha256:5116c66d...2697309`
- linux/arm64 manifest `sha256:733da1be...febe038d8`
- plus two attestation manifests.

Two consequences: (1) the repo's `image_digest` in `PROVENANCE.json` is the **index** digest, which is shared by both architectures; it does not identify the arm64 binaries. Add the platform and the per-platform manifest digest (arm64 `sha256:733da1be...`) to the provenance record. (2) `osrm_local.md` says the pinned image is "untested" on other machines; it is available for amd64, so the claim should read "untested", not "unavailable." The pinned release is v6.0.0; its release notes (https://github.com/Project-OSRM/osrm-backend/releases/tag/v6.0.0) mention "removed remaining CH code, leaving the MLD path" (SECONDARY via summary) and a flaky-test disablement; they say nothing about data-format or cross-architecture guarantees.

**5.2 Same pbf + same image version + same profile: identical travel times on x86-64? Not guaranteed; probably within 0.1 s per edge; untested.**
- Evidence that the upstream project sees platform-dependent rounding: PR #7627 "fix(extract): deterministic decisecond rounding in extraction + tests" (https://github.com/Project-OSRM/osrm-backend/pull/7627, VERIFIED page content). The author describes flaky 0.1 s differences on Ubuntu 26.04 CI attributed to platform-dependent rounding. The PR was **closed 28 Jun 2026 and the page does not show it merged**, and no final fix is confirmed; v6.0.0 (released 21 Apr, per the release page) predates it. So the shipped v6.0.0 extractor may still have platform-sensitive rounding (INFERENCE).
- Mechanism (HYPOTHESIS): OSRM computes edge durations in floating point and rounds to integer deciseconds. Compilers on arm64 fuse multiply-add by default; default x86-64 builds do not, so a value near a .5 boundary can round differently. Different rounding on a single edge shifts that edge by 0.1 s.
- Issue #5526 "Is OSRM with MLD deterministic?" (https://github.com/Project-OSRM/osrm-backend/issues/5526): a maintainer said routing output "should be deterministic" on one build, with rare snapping differences (about 0.0001%) tied to rounding when `overview` changes (VERIFIED). That is about repeated queries on one dataset, not cross-architecture rebuilds.
- Open issue #3769 "Flaky restricted turn test fails due to non-deterministic turn generation" (listed in a GitHub issue search; open at search time; VERIFIED title only) shows preprocessing itself can be order-dependent.
- Our own project log (A1) observed that a rebuild on the same machine gave **non-byte-identical** `.cell_metrics`/`.mldgr` (I could not re-verify; Docker was down and rebuilding is out of scope). Whether the resulting **travel times** differ was not recorded. This is the question that actually matters, and it is cheap to answer (section 5.5).
- Expected size of a difference (ESTIMATE): a few 0.1 s steps along a path of tens of edges, so well under 1-2 s on trips of several minutes. Scientifically negligible against the model's own error (free-flow vs evening-traffic factor, vans vs cars), but it breaks bitwise identity of the matrix.

**5.3 Can MLD files built on arm64 be served on amd64? Unknown; probably yes for same version, untested.** I found no OSRM documentation or issue that states cross-architecture compatibility or incompatibility of `.osrm.*` files (searches returned nothing; VERIFIED absence in what I searched, not proof). Both architectures are 64-bit little-endian, so a raw-memory/struct layout is likely compatible if the toolchains lay out structs identically (INFERENCE). The R package `osrm.backend` documents an error hint when a graph is incompatible with the installed OSRM **version**, which suggests version, not architecture, is the checked property (SECONDARY). Treat as HYPOTHESIS and test (5.5). Never mix OSRM versions.

1. **Canonical artifact = the matrix, not the server.** Share `tt_locations_v2.csv` (and `locations_snap_v2.csv`, `routes_M_v2.geojson`) with a recorded sha256 (current: `b24c0bc6c842988f3f67afb0378efb549ea108c30f3883b35fc604ccb15818db` for `tt_locations_v2.csv`, VERIFIED locally today), the pbf md5 (`ff90439cea505560649ac52f97b4ea42`), image tag, index digest and per-platform digest, profile, algorithm and platform of the builder. 2. Most teammates should **not** run OSRM at all; they run simulations from the committed matrix (data is gitignored today, so distribute the small CSVs with their hashes by other means, e.g. release asset; 35k rows is small).
3. Per-machine servers only for new coordinates. ## 6. Reproducibility

Pins and fingerprints:
- **Python:** the venv is 3.10.6 (VERIFIED). Python 3.10 reaches end of life in October 2026 (SECONDARY, PEP 619 schedule from memory), i.e., now. Do not upgrade mid-project; record the version in every output. (cuOpt would need 3.11+, another reason it is not a fit.)
- **Packages:** `requirements.txt` has only `folium>=0.20` and `pillow>=10` (VERIFIED), while the venv has about 50 packages (pandas, numpy, scipy, matplotlib, pytest, ...). **Disagreement with project docs:** requirements are neither complete nor pinned. Recommend an exact lock (`pip freeze` now, with versions numpy 2.2.6, pandas 2.3.3, scipy 1.15.3, etc.; optionally hashes via pip-tools), plus `highspy==<exact>` and any other solver added. Store the lock in the repo and the freeze output with each experiment.
- **Data fingerprints:** pbf md5, matrix sha256, snap file sha256, scenario file content hashes (generator already hashes content; per `phase3/plan.md` it has byte-identical rebuilds and separate streams per component).
- **Seeds:** use `numpy.random.SeedSequence(entropy=experiment_seed, spawn_key=(scenario_id_hash, replication, component_id))` with **named, fixed component ids** (arrivals, origins/destinations, party size, patience, driver response, Lyft pickup delay, solver). Do not rely on spawn order, so adding a component never shifts the others. Draw every policy-independent random quantity **per request, in advance**, not at event time, so that all arms see identical riders (common random numbers) and paired differences are valid. A policy that changes the number of draws would otherwise desynchronize the streams. Solver/heuristic randomness gets its own stream.
- **Determinism hygiene in code:** event queue ties broken by (time, priority, sequence id); simulate time in integer seconds or deciseconds (matrix values are 0.1 s resolution) to avoid float drift in tie-breaking; sort before iterating sets/dicts of ids; fixed `PYTHONHASHSEED`; `OMP_NUM_THREADS=1` in workers; heuristics break ties by id. Floating-point sums can differ across CPU architectures in numpy (SIMD dispatch; SECONDARY), so compare results across machines with a tolerance, and compare **within** a machine bitwise.
- **Environment capture per run:** write `run_manifest.json`: git commit and dirty flag, `pip freeze` hash, Python version, OS/arch (`platform.platform()`), CPU count, solver versions and options, MANIFEST.json hash of the data, all seeds, wall-clock and CPU time, solver statuses/gaps.
- **Tests that guard this:** run the same scenario twice and assert identical output hashes; run with worker counts 1 and 4 and assert identical results (catches shared-state leaks).

## 8. Matched computation budgets and what "optimal" means

- **A time-limited MILP is not automatically optimal.** If it stops at the time or node limit it returns an incumbent and a bound; the status is "limit reached". Even when it stops "optimal", HiGHS's default `mip_rel_gap` is 1e-4 (VERIFIED), so the claim is "within 0.01%", and for a nonlinear objective (e.g., TransLoc's convex wait penalty) the MILP optimizes a **piecewise-linear approximation**, so its optimum is only exact for that approximation (INFERENCE). Report status, gap and bound with every exact result, and say "proved optimal for objective X" only when the gap is closed.
- **Match budgets by a deterministic quantity, not only seconds.** Comparisons of heuristic vs MILP should show: (a) equal wall-clock on the same machine (what a practitioner sees), (b) equal node/iteration count (what is reproducible), and (c) the heuristic given many more iterations as an "almost-converged" reference. If the heuristic's budget is far smaller than the exact solver's, the comparison is about budget, not method; say so. TransLoc's stated example (12 rides, 1 vehicle, under 15 s, VENDOR 2016, transloc_operations.md section 3.2) is a calibration of what the real engine spends, but it does not tell us our simulator's heuristic budget; choose that explicitly and vary it.
- **Per-epoch optimality does not imply whole-night optimality.** (1) Each epoch is a snapshot: future arrivals, cancellations and no-shows are unknown, so minimizing the current plan's cost can leave vans badly positioned for later requests. (2) With reassignment every 2 minutes, an epoch-optimal plan can flip assignments between epochs and lengthen waits ("plan churn"); a good heuristic with a stability term can beat repeated exact optimization over the night (HYPOTHESIS; testable in the experiments). (3) Irreversible decisions (a Lyft transfer, a rider cancelling because of a long displayed ETA, a pickup already started) mean that today's optimum changes tomorrow's problem. (4) Objective mismatch: the epoch objective (weighted waits, ride times, mileage) is not the reported night-level outcomes (Lyft share, cancellations, wait/ride percentiles, and completed rides). (5) The only whole-night exact object is an **offline clairvoyant (hindsight) benchmark**, feasible only at L1-L4 size; it is a bound on what an online policy could achieve, not a policy, and it must not be presented as "the MILP policy".
- **Recommended framing for the report:** three references on L1-L4: greedy (floor), TransLoc-like heuristic T (baseline), epoch-exact MILP (per-epoch ceiling) plus the hindsight bound; at L6-L7 drop the exact claim and report T and variants against greedy and a long-run heuristic.
