## 1. What M6 is for
1. **Compute (the main purpose).** How long does C take on a full normal evening (168 requests, 18:00 until the backlog is done)? Is the time spread evenly over the evening, or bunched at the peak? That sets what M7 can afford.
2. **Demonstration.** One complete evening, start to finish, to show in the final talk: requests arriving, vans re-planned, riders reached or not, Lyft transfers.

**M6 is not a test.**
- **No hypothesis, no margin, no interval.** C and G both run so that the demonstration can show both on the same evening. Their difference over 5 nights is reported as description only. It is not evidence for or against anything (M5b is the evidence).
- **No Lyft-rule comparison.** Every M6 run uses R0, the no-transfer reference. So nothing seen in M6 can tilt the M7 rule comparison.

## 3. What is reported
**Compute** (`python -m sim.m6 report`, for every M6 night):
- wall time per night, and its median and maximum over the 5 nights;
- peak memory;
- number of re-plans, and the slowest re-plan;
- re-plan time by clock hour (18:00, 19:00, 20:00, then the backlog);
- solver status (every C re-plan should be proven optimal over its candidate set; any node-limit re-plans are counted);
- every run check.

**Outcomes:**
- **r00 (demonstration night):** C and G side by side (share not reached within 20 min, waits, rides, cancellations).
- **All 5 nights:** the same measures as a table, labelled descriptive: "5 nights, no interval, not a test".

**Check adapted for the full night:**
- **The issue:** the M5 run checks are reused unchanged, except one. "Backlog resolved after arrivals end (last request ≤ 3600 s)" assumes a first-hour slice.
- **Replacement:** M6 uses "backlog resolved after arrivals end (all 168 requests)", which checks that the run ended after every request's final outcome.
- **Code:** the check lives in `src/sim/m6.py`. The fingerprinted check code (`l5_pilot.py`) is not changed.

## 4. What M6's compute leads to (the team decides)
M7's size is set from M6's C time, before any M7 outcome exists, using:

*machine hours for M7 ≈ (number of C runs in the grid) × (M6's median C time per evening) ÷ (workers that fit in memory).*

| M6 median C time per full evening | Proposed reading for M7 |
|---|---|
| ≤ 30 min | A full-evening M7 grid is affordable on this laptop before 1 Dec, at a size the team sets from the formula |
| 30 min – 2 h | M7 must be small (few rules, few nights), or run on more machines after a cross-machine reproducibility check |
| > 2 h, or any night > 12 h | Revisit D-51 before M7 (D-51 item 3), not during it. Options: first-hour M7 only, or a faster dispatcher with its own frozen test (M5d's C-S6 if it qualifies) |

## 5. What M6 does not show
- Busy-night full evenings. These are not run (D-51 scope; compute).
- Anything about Lyft rules.
- That C beats G over whole evenings. Five nights with no interval is a demonstration, not evidence. M5b's first-hour test is the evidence.
- Anything about the real TransLoc dispatcher.
